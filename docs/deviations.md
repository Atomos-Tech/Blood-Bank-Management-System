# Deviations from Submitted SRS / SAD / Test Plan

This document records every technical deviation or refinement between the Part-1 specification documents (`1_Software_Requirements_Specification.pdf`, `2_Software_Test_Plan.pdf`, `3_Software_Architecture_and_Design_Specification.docx.pdf`) and the Part-2 implementation (`blood-bank-management-system/`), for explanation during the final evaluation demo.

Each row names the backlog item and test case it belongs to and where the change landed: a pull request number, or the commit hash for work merged directly on `main` during Sprints 0-1. Test case results are in [`docs/test-results/TEST_EXECUTION_RESULTS.md`](test-results/TEST_EXECUTION_RESULTS.md).

| 7 | **SRS FR-09** & **Test Plan TC-F06** | Unique donation ID and unique blood unit ID for every donation and derived component. | `services.record_donation` creates one `Donation` and one `BloodUnit` per prepared component (red cells, platelets, plasma) in a single transaction. The donation form takes one optional volume per component instead of a single component field. | Timestamp-only IDs could collide for donations recorded in the same instant, and one donation could only yield one unit. | 8 | **SADS 4.1 Unit State Machine** & **SRS FR-14** / **TC-F08** | Unit states limited to the defined lifecycle; invalid transitions rejected. | All unit status changes (screening, reservation, release, cancellation, issue, expiry, disposal) now go through `services.transition_unit`, which checks `UNIT_TRANSITIONS` (a direct copy of SADS 4.1). Staff discard `Quarantined`/`Expired` units from Inventory with a mandatory disposal reason. | Status fields were previously assigned directly, so nothing stopped an invalid move such as `Collected -> Issued`, and `Discarded` was never reachable. Auto-advancing to `Testing` keeps the SADS path intact without adding a separate "start testing" click. | `BB-21` (`#23`), `TC-F08` · Landed in: commit `45ebc08` |
| 9 | **SRS FR-12 / FR-13** & **Test Plan TC-F07** | Unit enters `Available` only after every mandatory result is acceptable; reactive, indeterminate or incomplete results quarantine it; procedure submits each result set and requests release. | Each recorded result is evaluated immediately: any non-acceptable mandatory result quarantines the unit, and the last acceptable result of a complete panel makes it `Available`. A separate **Release to inventory** action (`/inventory/<pk>/release/`) quarantines a unit whose panel is still incomplete, and release is refused when no mandatory panel is configured. Optional (non-required) test types never block release. | The previous logic re-evaluated after every result and quarantined a unit as soon as its *first* result was entered (the rest of the panel was still missing), so no unit could reach `Available` through the screening screen. | `BB-19` (`#21`), `BB-20` (`#22`), `TC-F07` · Landed in: commits `c50473a`, `39ca03b` |
| 10 | **SRS FR-16** & **SADS 3.4 Deployment View** / **TC-F08** | Unissued units marked `Expired` when expiry is reached; scheduled tasks run as a separate process. | New management command `expire_units` (optionally `--every N` seconds) and a `scheduler` service in `docker-compose.yml` that runs it every 5 minutes. The page-load check in inventory, dashboard and reservation is kept as a second safeguard. | Expiry previously happened only when someone opened the dashboard or inventory, so the stored status could be stale and an expired unit kept holding a reservation. | `BB-23` (`#25`), `TC-F08` · Landed in: commit `eea5e76` |
| 11 | **SRS SEC-07** & **SADS 4 Reporting and Audit Service** / **TC-S03** | Audit records include actor, event type, UTC time, record ID and outcome and are not editable; append-only application audit events. | `AuditEvent` refuses updates and deletes at model and queryset level (`ImmutableAuditRecord`) and refuses events missing an event type, record ID or outcome. | 19 | **SRS SEC-03** & **Test Plan TC-S01** | Lock an account for 15 minutes after 5 consecutive failed sign-ins within 10 minutes and record the event. | The counter and the lock moved from Django's default local-memory cache to a database-backed cache (`CACHES` in `bbms/settings.py`, table `bbms_cache` created by migration `0007`), so every worker process counts the same attempts. `services.record_login_failure` starts the ten-minute window at the first failure instead of pushing it forward with each one, so attempts spread more thinly than the limit never add up to a lockout, and it writes a `LOGIN_FAILED` event per attempt plus one `ACCOUNT_LOCKED` event on the lockout.
