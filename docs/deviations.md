# Deviations from Submitted SRS / SAD / Test Plan

This document records every technical deviation or refinement between the Part-1 specification documents (`1_Software_Requirements_Specification.pdf`, `2_Software_Test_Plan.pdf`, `3_Software_Architecture_and_Design_Specification.docx.pdf`) and the Part-2 implementation (`blood-bank-management-system/`), for explanation during the final evaluation demo.

| # | Document & Section | What Was Specified | What We Built / Refined | Why (Engineering Rationale) | Linked Backlog / Issues |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **SRS 2.4** (Operating Environment) & **SADS 11** (Design Decisions) | PostgreSQL as the primary relational database across environments. | Dual-mode database configuration in `bbms/settings.py`: uses **PostgreSQL 16** automatically when `BBMS_DB_ENGINE=postgresql` (as configured in `docker-compose.yml`), and **SQLite in WAL (`Write-Ahead Logging`) mode** for zero-config local evaluation and GitHub Actions CI. | Allows evaluators, developers, and CI runners to run `migrate`, `seed_demo`, and the full automated test suite out-of-the-box without requiring a local PostgreSQL daemon, while preserving production PostgreSQL support in Docker. | `BB-02`, `BB-38` (`#40`), `BB-39` (`#41`) |
| 2 | **SADS 5.1** (Database Constraints) & **SRS FR-22** | A conditional unique constraint prevents more than one active reservation for a unit. | Replaced the initial `OneToOneField(BloodUnit)` on `Reservation` with a `ForeignKey(BloodUnit, related_name="reservations")` plus a database-level partial unique constraint `UniqueConstraint(fields=["unit"], condition=Q(active=True), name="unique_active_reservation_per_unit")`. | An unconditional `OneToOneField` prevented a unit whose reservation was released (`active=False`) from ever being reserved again for another request (`TC-F13`). The conditional unique constraint enforces at most one active reservation while permitting re-reservation after release. | `BB-29` (`#31`), `TC-F13` |
| 3 | **SADS 8.2** (API Endpoint Summary) | 13 JSON endpoints under `/api/v1/...` alongside browser templates. | Server-rendered CSRF-protected Django views power all browser workflows, and the **Inventory & Request Service REST endpoints** (`GET /api/v1/inventory`, `POST /api/v1/requests`, `PATCH /api/v1/requests/{id}/status`, `POST /api/v1/requests/{id}/reserve`, `POST /api/v1/issues`) are implemented with SADS 8.3 standard error bodies (`code`, `message`, `field_errors`, `correlation_id`, `timestamp`) and `Idempotency-Key` support. | Prioritized complete server-rendered role workflows for the academic prototype while providing full SADS 8.2/8.3 JSON API compliance and idempotency for the Inventory & Request module (`FR-17` to `FR-24`). | `BB-24` (`#26`) to `BB-31` (`#33`) |
| 4 | **SRS FR-18** & **Test Plan TC-F10** | Scheduled task notifies designated staff on low stock and near-expiry units without duplicate alerts on repeated runs. | Implemented both as a callable service (`check_stock_and_expiry_alerts` / `get_branch_warnings` in `bloodbank/services.py`), a Django management command (`python3 manage.py check_alerts`), and a live warning banner on the Staff/Admin Dashboard (`dashboard.html`). Deduplication checks existing `(recipient, subject)` records in `Notification`. | Gives staff immediate visual visibility on the dashboard in addition to idempotent scheduled email notifications (`TC-F10`). | `BB-25` (`#27`), `TC-F10` |
| 5 | **SRS NFR-09** & **Data Model (SADS 5)** | Branch-level access restrictions for operational users across donors, inventory, requests, reports, and audit. | Added `Donor.branch` foreign key (migration `0002`) in addition to `BloodUnit.branch`, `Donation.branch`, `BloodRequest.branch`, `AppointmentSlot.branch`, and `AuditEvent.branch`, enforced by `user_branch()` and `in_branch_scope()` in `bloodbank/views.py`. | The original `Donor` model had no `branch` foreign key, which prevented filtering `/donors/` and `/deferrals/` by branch for operational staff (`BB-46` / `TC-S02`). | `BB-46` (`#48`), `TC-S02` |
| 6 | **Test Plan 6.17 & 6.18** (`TC-N01` & `TC-N02`) | 100 concurrent authenticated users against 5,000 donors and 10,000 units (`p95 <= 3s`), and concurrent reservation contention (`<= 5s`, `0` duplicates). | Provided both a `locustfile.py` script and a self-contained multi-threaded benchmark runner (`scripts/run_load_and_concurrency_benchmark.py`) that seeds 5,000 donors & 10,000 units, runs 100 concurrent authenticated sessions and 20-way reservation contention, and writes verified metrics to `docs/test-results/`. | Allows deterministic, reproducible verification of `NFR-01` and `NFR-02` inside CI and local test environments without external load-generation clusters. | `BB-38` (`#40`), `BB-39` (`#41`) |
| 7 | **SRS FR-09** & **Test Plan TC-F06** | Unique donation ID and unique blood unit ID for every donation and derived component. | `services.record_donation` creates one `Donation` and one `BloodUnit` per prepared component (red cells, platelets, plasma) in a single transaction. Donation IDs are `DON-<date>-<12 random hex>`; unit IDs append a component code (`-RBC`, `-PLT`, `-PLS`). A clash with the unique constraint is retried. The donation form takes one optional volume per component instead of a single component field. | Timestamp-only IDs could collide for donations recorded in the same instant, and one donation could only yield one unit. The component suffix lets staff trace any bag back to its donation and donor at a glance. | `BB-16` (`#18`), `TC-F06` |
| 8 | **SADS 4.1 Unit State Machine** & **SRS FR-14** / **TC-F08** | Unit states limited to the defined lifecycle; invalid transitions rejected. | All unit status changes (screening, reservation, release, cancellation, issue, expiry, disposal) now go through `services.transition_unit`, which checks `UNIT_TRANSITIONS` (a direct copy of SADS 4.1). Rejected attempts are written to the audit trail with outcome `REJECTED`. Screening moves a `Collected` unit to `Testing` automatically before the panel outcome is applied. Staff discard `Quarantined`/`Expired` units from Inventory with a mandatory disposal reason. | Status fields were previously assigned directly, so nothing stopped an invalid move such as `Collected -> Issued`, and `Discarded` was never reachable. Auto-advancing to `Testing` keeps the SADS path intact without adding a separate "start testing" click. | `BB-21` (`#23`), `TC-F08` |
| 9 | **SRS FR-12 / FR-13** & **Test Plan TC-F07** | Unit enters `Available` only after every mandatory result is acceptable; reactive, indeterminate or incomplete results quarantine it; procedure submits each result set and requests release. | Each recorded result is evaluated immediately: any non-acceptable mandatory result quarantines the unit, and the last acceptable result of a complete panel makes it `Available`. While the panel is still being entered the unit stays in `Testing`. A separate **Release to inventory** action (`/inventory/<pk>/release/`) quarantines a unit whose panel is still incomplete, and release is refused when no mandatory panel is configured. Optional (non-required) test types never block release. | The previous logic re-evaluated after every result and quarantined a unit as soon as its *first* result was entered (the rest of the panel was still missing), so no unit could reach `Available` through the screening screen. | `BB-19` (`#21`), `BB-20` (`#22`), `TC-F07` |
| 10 | **SRS FR-16** & **SADS 3.4 Deployment View** / **TC-F08** | Unissued units marked `Expired` when expiry is reached; scheduled tasks run as a separate process. | New management command `expire_units` (optionally `--every N` seconds) and a `scheduler` service in `docker-compose.yml` that runs it every 5 minutes. When a reserved unit expires, its active reservation is released and audited so the request can reserve a replacement. The page-load check in inventory, dashboard and reservation is kept as a second safeguard. | Expiry previously happened only when someone opened the dashboard or inventory, so the stored status could be stale and an expired unit kept holding a reservation. | `BB-23` (`#25`), `TC-F08` |
| 11 | **SRS SEC-07** & **SADS 4 Reporting and Audit Service** / **TC-S03** | Audit records include actor, event type, UTC time, record ID and outcome and are not editable; append-only application audit events. | `AuditEvent` refuses updates and deletes at model and queryset level (`ImmutableAuditRecord`) and refuses events missing an event type, record ID or outcome. The Django admin for audit events is view-only for every account, superusers included, and `/audit/` accepts GET only and shows times explicitly in UTC. System jobs such as the expiry task record a blank actor, shown as "System". Deleting a user still keeps their events, with the actor cleared. | The audit model was registered with the default editable admin, so any admin login could change or delete history. Blocking at the model layer protects against code paths outside the admin as well. | `BB-56` (`#58`), `TC-S03` |
| 12 | **SRS 6.3 Role Permission Matrix (Table 4)**, **SEC-01** & **TC-S02** | Every protected action checked on the server against the role-permission matrix; out-of-scope access denied and logged. | Views use role sets taken from Table 4: blood bank staff run donor, screening, inventory and request operations; hospital staff see restricted availability and create/track their own requests; donors see their own record and appointments; the administrator has oversight only (inventory view, reports, audit trail) plus configuration through Django admin. A superuser flag no longer bypasses these checks, and a superuser with no profile is treated as the administrator. Every denial, including an unknown request action, writes an `UNAUTHORIZED_ACCESS` audit event. The automated matrix test covers 26 protected URLs (web and API) for all four roles, anonymous users and out-of-branch staff. | `ADMIN` used to share the staff role set and the demo admin is a superuser, so the administrator could approve requests, screen units and view donor medical history, which Table 4 marks as "no routine access". The matrix test also found that `/requests/<id>/reserve/` was captured by the generic action route and always returned 403; the routes were reordered. | `BB-50` (`#52`), `TC-S02` |
| 13 | **SRS NFR-10** & **Test Plan TC-N07** | Record dates and times in UTC and display them in the branch time zone configured by the administrator. | `BranchTimezoneMiddleware` activates the logged-in user's `Branch.timezone_name` for each request, so pages and datetime form input use branch local time while the database keeps UTC. Users without a branch (e.g. the administrator) and unknown time-zone names fall back to UTC, and the page header names the zone in use. The audit trail is the one exception: it always shows UTC (SEC-07). `tzdata` was added to `requirements.txt` so slim containers and Windows hosts resolve zone names. | `Branch.timezone_name` existed but was never used, so every page showed UTC, and the request history labelled times "UTC" without converting them. | `BB-47` (`#49`), `TC-N07` |
| 14 | **SRS FR-01 / FR-03** & **Test Plan TC-F01 / TC-F02** | Registration validates identity, contact, consent and medical history; eligibility uses screening responses. | `DonorForm` makes consent, medical history and a fixed five-question screening questionnaire (`SCREENING_QUESTIONS` in `models.py`) mandatory, and validates phone format, date of birth (not in the future) and blood group (one of the eight ABO/Rh groups). Answers are stored in `Donor.screening_responses` (migration `0004`). A "Yes" to any question blocks eligibility and names only that question. | The SRS does not list the questionnaire items. A small fixed list keeps the prototype testable; the list can later move to administrator configuration with the other eligibility rules. | `BB-08` (`#10`), `BB-10` (`#12`), `TC-F01`, `TC-F02` |
| 15 | **SRS FR-03** & **SADS 5 Data Model** | Eligibility rules for age, weight, **donation type** and donation interval. | `Donation.donation_type` (whole blood, platelets, plasma) and per-type intervals on `EligibilityRule` (`minimum_interval_days` for whole blood, `platelets_interval_days`, `plasma_interval_days`; migration `0005`). `next_eligible_date()` applies the interval of each past donation. Weight has a configured minimum only; the "maximum" boundary in the backlog item is covered for age. | The original model had a single interval for all donations, so donation type could not affect eligibility. | `BB-10` (`#12`), `TC-F02` |
